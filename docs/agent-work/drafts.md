# Draft composition workstream scratchpad

## Objective and scope

Implement local encrypted draft composition for new messages, replies, reply-all, and forwards in `backend/src/main/java/com/east/app/drafts/`. Support To/CC/BCC, sanitized rich HTML and plain text, user-selected files, forwarded source attachments, explicit save to Gmail Drafts, explicit user-confirmed send, and durable reconciliation after uncertain Gmail side effects. Use the existing OAuth principal, Gmail API client, vault, and mail-read cache. Historical original implementation scope was backend drafts plus migration 003; the saved-draft send-race repair also updates `GmailApiClient`, this scratchpad, the Phase 2 acceptance note, technical/decision docs, and project progress. No live Google calls were made.

## Status

Draft composition is implemented. A follow-up hardening pass commits `SAVE_PENDING` or `SEND_PENDING` in a separate transaction before Gmail I/O, so another tab or a restarted process cannot repeat an uncertain side effect. Pending rows remain blocked until a user explicitly reconciles them. A PostgreSQL session advisory lock now enforces one East backend process per database; it is acquired before the embedded web server starts, held on a dedicated pooled connection, and released on shutdown. This makes the per-draft in-process active-operation guard sufficient for preventing reconciliation while Gmail I/O is running. After restart, the durable pending row remains and requires manual reconciliation. Attachment review fingerprints now bind SHA-256 digests of the actual staged/Gmail attachment bytes.

## Architecture and safety decisions

- Current app user comes only from `EastUserPrincipal.appUserId()`. Each operation checks mailbox/draft ownership in SQL and requires an unlocked vault.
- `EastSingleInstanceGuard` holds `pg_try_advisory_lock(0x45415354, 0x4c4f434c)` for the lifetime of the backend. A second process pointed at the same PostgreSQL database fails startup with a sanitized message; shutdown explicitly unlocks and closes the connection. The advisory lock is database-scoped, so different databases remain independent East installations.
- Access tokens come from `GoogleAccessTokenService#getValidAccessToken(UUID appUserId, UUID mailboxId)` and never reach the response.
- Draft payload is serialized and encrypted with vault AES-GCM. Its AAD binds app-user ID, draft ID, and mailbox ID. Each staged attachment has its own encryption and AAD binding app-user, draft, and attachment IDs.
- Multipart parsing is configured to remain in memory rather than spool plaintext uploads to disk. User uploads accept any extension, with a 10 MiB per-file, 16 MiB total and 10-file per-draft limit. East preserves a syntactically safe declared MIME type or uses `application/octet-stream`; outgoing uploads are not executed or previewed. A request is capped at 12 MiB.
- Rich HTML is parsed with Jsoup and allowlisted to basic formatting, links, lists, paragraphs, and line breaks. Scripts, styles, images, forms, and other unsupported markup/attributes are removed for local drafts. To/CC/BCC are validated email address lists; subject and filenames reject control characters/header injection.
- Gmail calls have no automatic retry. Sending requires `confirmed: true`, the exact local `updatedAt` revision the user reviewed, and a SHA-256 base64url `reviewFingerprint` over sender/mailbox, mode/source thread, Gmail thread/reply headers for replies, recipients, subject, plain/rich body, and ordered attachment filename/type/size plus SHA-256 content digests. East-local source-message UUIDs are excluded because Gmail's saved MIME cannot carry them; replies remain bound to the immutable East thread and Gmail threading headers. New/forwarded messages do not bind an API-assigned Gmail thread ID because Gmail can add one when saving the draft.
- Saved Gmail drafts are read with `GmailApiClient.getDraft(..., "full")` only when the user opens them, confirms send, or explicitly reconciles a saved operation. Ordinary review fetches attachment bytes only to hash them, wipes those arrays, and does not persist another local plaintext copy. HTML/header/MIME data that East cannot safely render for review yields 409. Before send, East re-reads the Gmail draft and re-hashes attachment bytes; edits invalidate the review. The send path builds a replacement MIME message from that verified snapshot and supplies both the Gmail draft ID and replacement `message.raw` to `drafts.send`, so Gmail sends the exact content East fingerprinted, even if another client edits the stored draft concurrently. Temporary attachment bytes are wiped when the send operation completes or fails.
- Replies preserve Gmail `threadId`, `In-Reply-To`, and `References`; reply creation is rejected if the source message has no usable Message-ID. Reply-all defaults to source Reply-To/sender plus other original To/CC participants. A reply/forward can use its encrypted cached body with `GmailCacheAad.message`; if expired, the user's explicit compose action fetches the source message from Gmail. Forwarding extracts attachment metadata from that full user-triggered read when cache metadata has expired, so the default-included files remain available. Sync caches selected header names in camelCase, so this workstream normalizes those aliases to Gmail header names.
- A Forward action fetches source attachment bytes only on user request, stages them encrypted, and returns removable attachment summaries. Missing declared size, >10 MiB each, >16 MiB total, or >10 files are rejected. User-selected/source attachment byte arrays are wiped after encryption, send, save, or failure cleanup.
- Successful Gmail save removes local encrypted payload and staged attachment bytes. East then reads the current Gmail draft in memory for review; successful send and deletion also remove local draft rows/bytes. No model/provider call is made in this phase. Draft/body/address/token values are not logged.
- Before each Gmail createDraft/sendMessage/sendDraft call, East commits `SAVE_PENDING` or `SEND_PENDING` and an operation timestamp in an independent `REQUIRES_NEW` transaction. The state survives process crashes and blocks all edits, saves, sends, and deletes from every tab/process. Gmail errors, missing confirmations, and local finalization failures leave the row pending and return HTTP 409 `DRAFT_RECONCILIATION_REQUIRED`.
- `GET /api/v1/drafts/{draftId}/reconciliation` returns `{ draftId, required, inProgress, operation, state, previousState, startedAt }`; `inProgress` is true while the current backend process is executing the Gmail call. Draft-list entries also include reconciliation operation/time. A normal draft GET returns 409 for pending rows. Clients should show recovery status and suppress the composer actions while pending.
- `POST /api/v1/drafts/{draftId}/reconciliation` accepts `{ confirmed: true, resolution: "CONFIRMED_COMPLETED"|"CONFIRMED_NOT_COMPLETED", gmailDraftId? }`. Reconciliation conflicts while `inProgress` is true. For a completed save, East can search up to 50 recent Gmail drafts matching the sender and subject and compare full content/attachment digests; if exactly one matches it links automatically. Otherwise the user can open the matching Gmail draft and copy its ID from the draft's address-bar URL (no developer tools needed). East verifies that ID's content before clearing local encrypted data. For a completed send, the user must attest that they found the message in Gmail Sent before East deletes the local row. To restore after confirming no side effect, the user must attest they checked Gmail; a saved-send can only be restored if that same Gmail draft still exists. Pending state is never auto-reset after timeout, shutdown, or restart.

## Endpoint contract

Base path: `/api/v1/drafts`. All endpoints require an authenticated app session and unlocked vault. Unauthorized requests return 401; locked vault returns 423. Ownership failures are 404. Error shape is `{ errorCode, message }`.

- `GET /api/v1/drafts` → `DraftListItem[]`, each containing `id`, `mailboxId`, `kind` (`NEW|REPLY|REPLY_ALL|FORWARD`), `state` (`LOCAL|SAVED_TO_GMAIL|SAVE_PENDING|SEND_PENDING`), `sourceThreadId`, `attachmentCount`, `createdAt`, `updatedAt`, `savedAt`, `reconciliationOperation`, and `reconciliationStartedAt`.
- `POST /api/v1/drafts` → 201 `DraftResponse`. JSON request: `{ mailboxId, kind?, sourceThreadId?, sourceMessageId?, to?, cc?, bcc?, subject?, plainTextBody?, richTextHtml? }`. `kind` defaults to `NEW`; non-NEW kinds require an owned source thread/message in the selected mailbox. Replies prefill recipients and quote source content; forwards quote source content and stage original attachments by default.
- `GET /api/v1/drafts/{draftId}` → `DraftResponse`: `{ id, mailboxId, fromAddress, kind, state, sourceThreadId, sourceMessageId, to, cc, bcc, subject, plainTextBody, richTextHtml, attachments:[{id,filename,mimeType,byteSize}], createdAt, updatedAt, savedAt, reviewFingerprint }`. For `LOCAL`, content is decrypted only for the owner while unlocked. For `SAVED_TO_GMAIL`, content and attachment data needed for hashes are read from the current Gmail Draft resource in memory. Pending states return 409 and should be handled using the reconciliation endpoint. The fingerprint is opaque and must be retained with the exact displayed response used for send review.
- `PUT /api/v1/drafts/{draftId}` → `DraftResponse`; replaces complete editable fields, preserving immutable source mode/thread/message and reply headers. A reply/forward cannot move to another mailbox. Saved Gmail drafts are read-only in East; edit them before save or in Gmail.
- `DELETE /api/v1/drafts/{draftId}` → 204; deleting a saved draft explicitly deletes the matching Gmail Draft resource before removing East's local reference.
- `POST /api/v1/drafts/{draftId}/attachments` (`multipart/form-data`, field `file`) → 201 `DraftAttachmentSummary { id, filename, mimeType, byteSize }`.
- `DELETE /api/v1/drafts/{draftId}/attachments/{attachmentId}` → 204.
- `POST /api/v1/drafts/{draftId}/save-to-gmail` → `{ id, state: "SAVED_TO_GMAIL", gmailDraftId, savedAt }`. The save click is separate from sending. After success, the client should GET the draft again to render the current Gmail copy and its new review fingerprint.
- `POST /api/v1/drafts/{draftId}/send` request `{ confirmed: true, expectedUpdatedAt: "<ISO-8601 timestamp from reviewed response>", reviewFingerprint: "<43-character base64url SHA-256>" }` → `{ id, state: "SENT", gmailMessageId, sentAt }`. A missing/false confirmation or malformed fingerprint is 400; stale local revision or changed/unparseable Gmail content is 409. Local drafts use Gmail `messages.send`; saved drafts are re-fetched, fingerprint-checked, rebuilt from the reviewed snapshot, and sent with the draft ID plus replacement message in one Gmail `drafts.send` request. Successful send removes the local record/staged bytes.
- `GET /api/v1/drafts/{draftId}/reconciliation` reports the durable pending operation and previous state. `POST /api/v1/drafts/{draftId}/reconciliation` requires `{ confirmed: true, resolution, gmailDraftId? }`; use `CONFIRMED_COMPLETED` after checking Gmail (the server searches for one matching save when no ID is supplied) or `CONFIRMED_NOT_COMPLETED` only after checking the relevant Gmail folder. Pending states block all repeat mutations server-side.

Known error codes include 400 `INVALID_DRAFT`, 401 `AUTHENTICATION_REQUIRED`, 404 `DRAFT_NOT_FOUND`, 409 `DRAFT_STATE_CONFLICT` or `DRAFT_RECONCILIATION_REQUIRED`, 413 `ATTACHMENT_TOO_LARGE`, 423 `VAULT_LOCKED`, and 502 `GMAIL_API_ERROR`/`DRAFT_OPERATION_FAILED` or mailbox authorization error. Validation and provider errors never include message bodies, addresses, attachment bytes, or credentials.
