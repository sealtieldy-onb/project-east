# Phase 2 Gmail sync acceptance audit

Date: 2026-11-09
Scope: source/docs-only audit of the 15-minute sync, initial 30-message baseline, on-start behavior, user-requested refresh, report-fetch boundary, per-mailbox failure handling, and revoked/expired authorization. No secrets, browser, Gmail APIs, live mailbox data, database, tests, or builds were accessed or run.

## Findings

| Requirement | Source status | Evidence and limits |
|---|---|---|
| Sync each linked mailbox every 15 minutes while East runs | Implemented in source | `EastApplication.java:7-9` enables scheduling. `GmailSyncService.java:87-99` runs at startup and then uses a fixed 900,000 ms delay, skipping while the local key is unavailable. `syncConnectedMailboxes()` reads connected targets and processes them one at a time (`:101-120`), checking key availability between targets. This is fixed delay after a run completes, not fixed-rate wall-clock scheduling. Exact cadence was not measured live. |
| Initial sync is bounded to the latest 30 messages per mailbox | Implemented in source | `GmailSyncService.java:51,269-311` limits distinct Gmail message IDs to 30, paginates only until the limit, fetches labels/content for those descriptors, and persists the captured starting history cursor. The pre-enumeration cursor lets later history sync replay changes that arrive during initial sync. Prior live sign-in/sync results are recorded in `docs/project-progress.md`; the exact 30-message DB/runtime count was not verified during this audit. |
| Incremental sync, stale history fallback, and mailbox isolation | Implemented in source | `historySync()` pages Gmail history, persists changes/deletions, and advances the cursor only after all pages (`GmailSyncService.java:314-373`). A 404 on the first history page falls back to the bounded initial sync (`:332-335`). `syncConnectedMailboxes()` records each target's result independently (`:101-120`); one failure does not abort processing later targets. No injected live stale cursor or per-account failure was tested. |
| Sync on startup and visible first-sync/manual refresh | Implemented in source; live UI flow partly evidenced | The startup scheduler has zero initial delay (`GmailSyncService.java:87-91`). The app also requests a per-mailbox sync where `lastSyncAt` is null (`frontend/src/App.tsx:473-482`). Dashboard per-account **Sync now/Refresh** calls the authenticated mailbox sync endpoint (`ConnectedDashboard.tsx:88-97`; `App.tsx:404-439,609-612`; `ManualMailboxSyncController.java:31-49`). It reports synced/in-progress/locked/missing/failure outcomes in the visible notice. Prior user-confirmed sync success is in the progress log; a separate explicit manual-refresh click was not confirmed in this audit. |
| Ask before fetching beyond 30 messages for the first 30-day report | Phase 3 requirement; correctly absent from Phase 2 | The product plan defines the 30-message sync baseline and says to ask before fetching beyond it for a 30-day report (`docs/product-plan.md:47-50`). The implementation roadmap places that one-time report and confirmation under Phase 3 (`docs/implementation-roadmap.md:71-80`); Phase 2 keeps AI reporting unavailable (`ConnectedDashboard.tsx:35-42`). No report-specific fetch path exists in the Phase 2 sync service. Full-mailbox folder/search browsing may request Gmail thread metadata on demand; that is separate from reading additional bodies for a report (`docs/implementation-roadmap.md:57,61-62`; `docs/technical-plan.md:73-80`). Preserve the explicit confirmation when Phase 3 adds report expansion; do not expand the background 30-message body sync. |
| Revoked/expired Gmail authorization is visible and prompts reconnection | Implemented in source; migration applied; real-401 acceptance pending | Migration 008 adds `sync_status`; the summary exposes it. Scheduled/manual sync handles 401 in `GmailSyncService`; all mailbox-scoped Gmail request paths in read/list/search/labels, actions, attachments, and draft/source operations now use `GmailRequestGuard` to invalidate the cached bearer token and set `reauthorization_required` plus `needs_reauthorization`. Invalid refresh grants use the existing same status path. The Dashboard consumes this state and shows a reconnect notice/action. No real 401 was induced. |
| Failed periodic sync status is visible to the user | Ready state verified; failure states source-implemented | Migration 008 and `GmailSyncRepository` persist `syncing`, `ready`, `partial_failure`, and `error` transitions. History failures become `partial_failure` only after committed message/deletion chunks. The Dashboard renders these states and refreshes the current mailbox summary every 30 seconds while the tab is visible. Changeset 008 was applied to the configured DB, and a fresh disposable database applied 001–008 successfully on 2026-11-09. After the user signed in again, the Dashboard displayed both connected accounts as Synced. Failure-state presentation remains unverified. |

## Runtime verification gaps

- The prior progress log records successful Google sign-in, two linked accounts, sync completion, and metadata browsing. This source audit did not contact Google or inspect account data.
- The 15-minute interval, automatic startup retry after a backend restart, and independent failure behavior for two accounts were not measured end to end.
- Manual per-account refresh, the 30-message initial baseline, invalid-grant reconnect, resource-level 401, and stale history cursor fallback have not been independently exercised in runtime acceptance.
- At the original sync-state checkpoint, the backend suite passed 21 tests. The later cross-endpoint authorization follow-up and final 27-test pass are recorded below. The 15-minute cadence and Gmail 401 flows have not been exercised live.

## Recommended next work

1. Configured-database migration 008, the post-sign-in Dashboard display of both accounts as Synced, and a fresh disposable-database migration through 008 are verified.
2. Keep live 401, invalid-grant, exact cadence, and two-account failure-isolation checks deferred unless they can be exercised safely without revoking access or modifying mailbox state.
3. Keep the Phase 3 report confirmation as a separate gate before any fetch beyond the initial 30 messages for AI analysis. Ordinary user-requested Gmail metadata search/browsing is not that report-fetch path.

## Backend sync-state implementation — 2026-11-09

- Added `MailboxSyncStatus`, Liquibase 008 with existing-row backfill, per-mailbox state transitions, lowercase `syncStatus` on the mailbox summary, and sync-resource HTTP 401 token invalidation/reauthorization persistence. Retryable 429/5xx/runtime errors remain `error`; page-data commit tracking distinguishes `partial_failure`.
- Added `GmailSyncStateTest`, `GoogleAccessTokenServiceReauthorizationTest`, and `MailboxSyncStatusJsonTest`. `mvn -o -B -f backend/pom.xml test` passed 21 tests, 0 failures/errors/skips.
- Added frontend parsing with backward-compatible fallback for pre-008 responses, Dashboard status rendering and reconnect action, pending initial-sync recovery, and a visible-tab 30-second mailbox-summary refresh. `npm run build` passed with 2,078 modules transformed.
- An independent source review found no migration/schema blocker and initially identified that non-sync 401s were not persisted. The cross-endpoint guard below closes that source gap; runtime behavior remains unverified.
- Added `GmailRequestGuard.call/run` and wrapped all owner/mailbox-scoped Gmail API calls across read/list/search/labels, actions, attachment, draft, and draft-source paths. Only 401 invalidates the cached token and persists reconnection state; the original Gmail exception is rethrown, non-401 behavior stays unchanged, and no request is retried. Scheduled/manual sync retains its existing handler.
- Mail-read, mail-action, and draft exception handlers now return HTTP 401 with the safe `MAILBOX_AUTH_REQUIRED` code for upstream Gmail 401s, instead of a generic gateway error. This lets Conversations direct users to the mailbox reconnect banner while preserving generic errors for non-401 provider failures.
- Source-only review; no tests, DB/Gmail/browser/secrets access, or service restart was performed for the guard or response mapping. Offline Maven compilation passed for all 116 backend sources with tests skipped, and `npm run build` passed with 2,078 modules; the earlier 21-test suite does not cover this wrapper.
- No live DB migration or Gmail 401 was performed. The frontend build does not prove status behavior against the new API; once the backend is restarted, the user will need a fresh Google sign-in.
