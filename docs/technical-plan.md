# Technical plan

## 1. Proposed technology stack

| Area | Proposed choice | Purpose |
| --- | --- | --- |
| Backend | Java, Spring Boot | Local HTTP API, OAuth callbacks, Gmail integration, sync orchestration, and application rules |
| Frontend | React, TypeScript, Vite | Local web interface for Dashboard and Conversations |
| UI | shadcn/ui with Tailwind CSS | Reusable, accessible interface primitives styled within the app |
| Database | PostgreSQL | Users, linked mailboxes, cached message metadata/content, labels, sync cursors, summaries, and insights |
| Schema migrations | Liquibase | Versioned and repeatable schema changes across local setups |
| Persistence | Spring JDBC (`JdbcTemplate`) | Explicit SQL for PostgreSQL-specific upserts, data-retention cleanup, and ownership-scoped Gmail queries; Liquibase remains the schema authority. |
| Email access | Gmail API | Read mail and, in later phases, perform explicitly enabled label/draft/send operations |
| Model integration | OpenAI plus a configurable OpenAI-compatible endpoint | The user supplies a model API key and, for a custom endpoint, its base URL and model identifier in local settings. Keep an adapter boundary so native integrations for more providers can be added later. |

The app runs locally on the user's computer. During development, the React dev server and Spring Boot service bind to the loopback interface and run on localhost, and Docker Compose runs PostgreSQL as a local service. Do not expose the app to other devices on the local network. No cloud hosting or deployment pipeline is required for the initial application.

For the initial implementation, use Java 21 and Spring Boot 4.1.2, which are compatible with the installed Java runtime. Use Spring JDBC with explicit SQL instead of JPA for the current PostgreSQL schema. Use Vite with React and TypeScript, Tailwind CSS, and shadcn/ui for the frontend. Pin versions in the build files and update them deliberately. See the current [Spring Boot reference](https://docs.spring.io/spring-boot/) and [Vite guide](https://vite.dev/guide/) for the supported setup.

## 2. Application shape

Use a simple local, single-repository setup with independently running frontend and backend processes:

```text
React + TypeScript + shadcn/ui
          │ HTTP, JSON
          ▼
Spring Boot API ───── Gmail API
     │                    ▲
     ├── PostgreSQL        │ OAuth tokens
     └── assistant jobs ───┘
```

- React owns presentation, navigation, filters, forms, and client-side interaction state.
- Spring Boot owns Google OAuth, user/session checks, authorization, Gmail API calls, business rules, data validation, summary orchestration, and access to secrets.
- PostgreSQL is the durable source for the app's users, linked mailbox records, sync cursors, normalized mailbox data that the app chooses to cache, and generated insights.
- Gmail remains the source of truth for mailbox messages and Gmail labels. Cached data is a read/sync layer, not an independent replacement mailbox.
- Keep the initial backend as a modular Spring Boot service. A separate worker process or queue can be added only when sync/summarization volume makes it necessary.
- Run one East backend process per local PostgreSQL database. A PostgreSQL session advisory lock acquired before the web server starts prevents a second process from reconciling an uncertain Gmail operation while the first process is still making the Gmail call.
- Store `HttpSession` through Spring Session JDBC in the same local PostgreSQL database using Boot 4's `spring-boot-starter-session-jdbc` auto-configuration. The direct `spring-session-jdbc` module alone does not activate Boot's JDBC session repository in this project; do not use the legacy `spring.session.store-type` property. This preserves the authenticated Spring Security context and session-bound OAuth state across backend restarts. Encrypt serialized session attribute bytes with the installation vault key using AES-GCM and a versioned envelope whose header and domain are authenticated as associated data; wipe serialization and cryptographic temporary buffers. If the key is unavailable or an old attribute cannot authenticate, treat that attribute as absent so vault status, unlock, and reset remain reachable. Use a 60-day inactive-session timeout and a 60-day cookie max-age; explicit logout invalidates the server-side session. Keep the `EASTSESSION` cookie HttpOnly and SameSite=Lax, retain `ChangeSessionIdAuthenticationStrategy` and the existing CSRF protections, and create the Spring Session tables only through Liquibase changeset 010. Require the Base64-encoded cookie payload to be a canonical UUID session ID, and expire any malformed or legacy value before Spring Session can pass it to JDBC. The database's session ID remains an opaque bearer lookup value needed by Spring Session, and its principal index contains only the internal app-user UUID; do not claim the entire Spring Session row is encrypted.

## 3. Local authentication and mailbox linking

Google sign-in and Gmail mailbox access are related but distinct product actions:

The initial local application supports one signed-in app user per installation. The data model and authorization checks remain user-scoped, and that user can connect multiple Gmail mailboxes. The first Google OIDC identity anchors the local app user; a different identity cannot replace it without the warned destructive local reset.

1. **App sign-in:** use Google OpenID Connect (`openid`, `email`, `profile`) to establish which user is using the local app. Validate the ID-token signature, issuer, audience, expiry, and nonce. Store Google's stable subject identifier as the provider identity. Email is display data, not the identity key.
2. **Connect mailbox:** run a separate authorization flow for each Gmail mailbox and associate its Google account subject and mailbox email with the signed-in application user. Bind the flow to the current app session and use Google's `select_account` prompt so the user can choose a different Google account without replacing the app identity.
3. **Local callback:** use Google's web-server OAuth flow with a web application client. The default redirect URI is `http://localhost:8080/login/oauth2/code/google`; if the local backend uses another port, set `EAST_GOOGLE_REDIRECT_URI` to that port and register the same exact URI in the Google Cloud project. Use `localhost` consistently in the browser and callback; do not mix it with `127.0.0.1`. Spring Boot handles the callback and code exchange. OAuth client credentials are local configuration, never source code.
4. **OAuth safety:** use a cryptographically random, one-time `state` bound to the browser session and validate it on callback. For OIDC sign-in also generate and validate `nonce`; verify the granted scopes and handle OAuth errors and revocation. Request offline access for the 15-minute sync and store refresh tokens on the server side.
5. **Credentials:** encrypt refresh tokens at rest using an application secret supplied outside version control. Never send refresh tokens to the React client, render them in logs, or include them in browser storage.

App sign-in and mailbox linking use the same fixed OAuth callback URI, but each session-bound authorization request records a separate intent (`sign_in` or `link_mailbox`). Validate one-time `state` for both flows and OIDC `nonce` for both ID tokens. The link flow carries the current app-user ID in server-side session state; never accept a target user ID from the browser.

Google may omit a refresh token on repeat authorization. Keep a previously stored refresh token when a later token response omits one; handle revoked/expired tokens by marking the mailbox as requiring reauthorization. During OAuth consent-screen Testing, Gmail-scoped refresh tokens for an external app expire after seven days, so local development must expect frequent reauthorization unless the consent screen is moved out of Testing. Google also limits refresh-token issuance per account/client. See [Google OAuth 2.0 for web server applications](https://developers.google.com/identity/protocols/oauth2/web-server), [OAuth policies](https://developers.google.com/identity/protocols/oauth2/policies), and [Google OAuth best practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices).

## 4. Gmail scopes and review implications

Use the minimum scopes needed for the feature the user is authorizing. Phase 2 includes reading/search, Gmail labels and mailbox actions, draft creation, and user-confirmed sending, so the mailbox-link flow requests `gmail.modify`. Do not request Gmail access during identity-only app sign-in; request it only when the user explicitly connects a mailbox.

| Capability | Candidate scope(s) | Notes |
| --- | --- | --- |
| Google app sign-in | `openid`, `email`, `profile` | Identity only; does not grant access to Gmail content. |
| Gmail-connected Phase 2 workflows | `https://www.googleapis.com/auth/gmail.modify` | Restricted scope; supports reading mail plus label, read-state, archive/trash/spam, draft, and send operations in the selected Phase 2 release. It is broader than `gmail.readonly`; the app must enforce explicit user action for every mailbox mutation and message-specific confirmation for send. |
| Identity-only app sign-in | `openid`, `email`, `profile` | Identity only; does not grant access to Gmail content. |

Google classifies `gmail.modify` as a restricted scope. OAuth projects in Testing can be limited to configured test users; development tokens with Gmail scopes may expire after seven days. Public apps requesting Gmail scopes may need OAuth verification. Apps that access restricted data through a third-party server may also need Google's security assessment. Review Google's current [Gmail scope list](https://developers.google.com/workspace/gmail/api/auth/scopes), [OAuth verification requirements](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification), [OAuth policies](https://developers.google.com/identity/protocols/oauth2/policies), and [Google API Services User Data Policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy) before enabling real accounts beyond local development.

The local app uses the web-server OAuth flow: Spring Boot handles the OAuth code exchange at the registered localhost callback. See the [Google OAuth setup guide](google-oauth-setup.md) for consent-screen, test-user, callback, and local `.env` setup. Google recommends different OAuth client types and PKCE considerations if East is later distributed as a desktop application; do not ship a shared web-client secret in a bundle. See Google's [web-server OAuth guide](https://developers.google.com/identity/protocols/oauth2/web-server) and [OAuth best practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices).

## 5. Gmail synchronization

- First connection performs a bounded initial sync for the latest 30 messages per mailbox, using pagination and storing the latest usable history cursor.
- Folder/category/filter pages use on-demand paginated Gmail thread metadata, not only the bounded sync cache. Keep each page bounded, merge selected mailboxes by latest message time, and retrieve bodies only when a user opens a thread. This does not fetch extra body content for Phase 3 reports without the required user confirmation.
- When a mailbox is linked, prompt the user to request a one-time report covering the past 30 days. Before content processing, an explicit metadata-only preview reports the eligible-message count for the selected mailbox/date scope without fetching bodies or calling the model. The UI discloses that count and the configured provider/model/destination; if the count changes before confirmation, show the new count and require confirmation again.
- Apply the initial 30-message body allowance per selected mailbox. If producing a report requires additional bodies, ask before fetching them; cap one manual expansion at 240 additional bodies across the selected scope and disclose the cap. If the user declines or the cap leaves eligible messages unread, generate from approved inputs and mark the report as partial with its actual coverage.
- Daily reports use the opt-in schedule's local calendar day for the previous-day window, consume only unexpired locally cached bodies, and select at most 240 bodies globally with a fair per-mailbox ordering. Dashboard date filtering recognizes a scheduled report by its local report date.
- Persist Gmail IDs and history state so messages can be updated without duplicates.
- Cache full message bodies only in encrypted local storage. The default lifetime is 60 days and the user can change it in settings. After a body expires, retain only minimal metadata needed for inbox/navigation (Gmail IDs, sender, subject, date, and labels). Purge snippets, attachment metadata/bytes, summaries, action items, and transaction insights with the user-configurable body-cache lifetime; an explicit attachment re-fetch after that point starts a fresh attachment metadata/byte TTL. Never use logs as a body cache.
- For structure-only background sync, represent an unfetched message body with an encrypted `ON_DEMAND` marker whose body expiry equals its cache timestamp so a thread open fetches it immediately. Keep the encrypted Gmail snippet on its own configured TTL so inbox preview text remains available until body-cache expiry. Liquibase changeset 006 allows equal body timestamps only for `ON_DEMAND` and `SYNC_LIMIT_ON_DEMAND`; all ordinary body cache entries must still expire after they are cached.
- For later changes, use Gmail history-based partial synchronization from the last stored `historyId`.
- If Gmail reports that a saved history cursor is no longer available, fall back to a bounded full sync and report its status.
- Store per-connected-mailbox sync state as `pending`, `syncing`, `ready`, `needs_reauthorization`, `partial_failure`, or `error`. A missing mailbox connection represents `not_connected`. Preserve these durable statuses for scheduled and user-requested syncs without storing provider error bodies or mailbox content.
- Keep sync isolated per mailbox so one account's failure does not hide data from other accounts.
- Sync each connected mailbox every 15 minutes while the app is running and provide an explicit refresh action. If the app was closed, sync on startup. Add Gmail push notifications only if local networking, Pub/Sub configuration, and product value justify them; push needs an externally reachable subscriber endpoint, so it is not assumed for the local proof of concept.
- Background sync requests Gmail MIME structure and attachment metadata with a partial-response field mask that excludes every `body.data` field. When a user opens a conversation, East fetches each message body separately, retains only decoded text content, and removes all MIME `body.data` fields before encrypting the body cache. Gmail's partial-response selector applies a selection to every element of a MIME `parts[]` array; it cannot select one array element by `partId`.
- Attachment rows use Gmail's external `attachmentId` when available, or `inline:<partId>` for a named inline part whose bytes are in its message body. A user click on an inline attachment fetches that message and extracts the selected `partId`; Gmail may include `body.data` for other MIME parts in the response, but East retains/returns only the selected part. The response byte buffer is zeroed after parsing; Jackson's immutable text values can only be dereferenced for garbage collection, not overwritten in place. Forwarding explicitly stages source attachments only after the user chooses Forward. No attachment bytes are sent to the AI provider.
- The recursive Gmail field mask covers MIME nesting through 24 levels. Parts nested deeper than that are not surfaced by current attachment metadata/read paths and require a future strategy. Inline attachment responses are bounded by East's local response and file-size limits; unusually large messages with many inline parts can therefore fail the explicit attachment request safely.

Google documents full/partial sync using Gmail history IDs and notes that a full sync is needed when the cursor falls outside available history. See [Synchronize clients with Gmail](https://developers.google.com/workspace/gmail/api/guides/sync) and [Gmail push notifications](https://developers.google.com/workspace/gmail/api/guides/push).

## 6. Initial domain model

All mailbox data must be scoped through the signed-in app user. Use generated internal IDs; never make a mailbox email address a database primary key. Assign each connected mailbox a stable distinct display color based on mailbox data rather than a hardcoded account list.

- `app_user`: internal ID, Google OpenID subject, display name, created/updated timestamps.
- `connected_mailbox`: internal ID, `app_user_id`, Google account subject, current email/display name, generated color, granted scopes, encrypted refresh token, connection/sync status, last sync time, Gmail history cursor.
- `mail_thread`: internal ID, `mailbox_id`, Gmail thread ID, subject and participant summary, snippet cache and expiry, timestamps, and label/read status as appropriate. Retain subject, participants, identifiers, dates, and labels for navigation after the body expires; expire snippets with the body cache.
- `mail_message`: internal ID, `thread_id`, `mailbox_id`, Gmail message ID, minimal sender/recipient metadata, date, headers needed by the product, encrypted body cache and expiry timestamp, Gmail label IDs, and size/content metadata. The default body cache lifetime is 60 days and is user-configurable.
- `mail_attachment`: message reference, Gmail external attachment ID or reserved inline part ID, filename, MIME type, and size metadata needed for display. Expire attachment metadata and bytes with the same user-configurable lifetime as message bodies. Fetch bytes only after the user opens/downloads the attachment or explicitly forwards its message; encrypt them while cached. If a user explicitly re-fetches an attachment after the source body-cache expiry, that click starts a new attachment TTL; pre-expiry cached bytes are never returned after source expiry. Do not send attachment contents to AI providers in the first release.
- `mail_label`: internal ID, `mailbox_id`, Gmail label ID, name, type, color when available.
- `summary_run`: user/mailbox or combined scope, requested period, actual input range and coverage status, model/ruleset version, status, created time, and expiry aligned with source body cache.
- `summary_run_source`: one record for each message body used by a report, with composite foreign keys that keep the report, app user, mailbox, and message aligned. Recalculate a narrative's expiry from the earliest source-body expiry when the cache lifetime changes, and delete any report referencing a mailbox before disconnect cascades its source rows.
- `summary_schedule`: user, enabled state, selected local time and timezone, report window, and last-run status for optional daily reports.
- `insight`: summary run, category (`summary`, `action_needed`, `awaiting_reply`, `response_received`, `transaction`), source message/thread references, structured result, confidence/evidence, status (`open`, `dismissed`, `handled`), and expiry aligned with source body cache.
- For combined runs, populate `summary_run_source` for every included source message, including inputs used only by the narrative. Insight-level source links remain available for evidence and per-insight expiry; mailbox disconnect removes the whole affected report and its insights.
- `draft`: user, required sending `mailbox_id`, optional source thread/message, encrypted To/CC/BCC recipient lists, subject, sanitized rich-text HTML and plain-text body, composition mode (`new`, `reply`, `reply_all`, `forward`), draft origin, status and timestamps. A new message uses the selected Conversations account or requires the user to choose one; replies and forwards default to their source thread's mailbox. Retain an app-local draft until it is saved to Gmail Drafts or deleted; it does not expire with the message-body cache. Sending state should only be recorded after a user-confirmed send operation succeeds.
- `draft_attachment`: app draft reference, source Gmail attachment ID or user-selected file name, MIME type, size, origin, and encrypted bytes while staged in an unsaved app-local draft. Include source attachments by default for a user-created forward draft; let the user remove them. Keep staged bytes until the draft is saved to Gmail, successfully sent, or deleted, then remove the local copy.

Relationships should use foreign keys and indexes for mailbox ownership, message/thread lookup, and time-ordered inbox views. Define deletion and retention rules before storing message bodies long-term.

## 7. API outline

Initial APIs can use REST with JSON and versioned `/api/v1` routes:

- `GET /api/v1/me` — current signed-in user and connected mailbox summaries.
- `GET /api/v1/vault/status`, `POST /api/v1/vault/unlock`, and `/reset` — local encryption-key status, one-time migration for legacy passphrase-encrypted data, and destructive reset. New installations create and load a random local key automatically. Reset requires the exact confirmation `RESET LOCAL DATA`. Google sign-in and Gmail APIs require the server-side app session and an available local encryption key.
- `GET /api/v1/auth/configuration` — report whether Google OAuth is configured without returning the client secret.
- `GET /api/v1/auth/google/start` — start Google OIDC app sign-in and redirect to the identity provider.
- `GET /login/oauth2/code/google` — the exact callback for both sign-in and mailbox linking; route by the validated, one-time state stored in the server-side session.
- `POST /api/v1/auth/logout` — clear the local authenticated session.
- `GET /api/v1/settings/ai-provider` — provider type, endpoint/model metadata, and booleans indicating whether a key is configured; never return a stored key.
- `PUT /api/v1/settings/ai-provider` — add/replace provider metadata and encrypt the supplied OpenAI-compatible API key through the local encryption key before persistence. Omitted keys preserve the existing key. `DELETE` removes the provider key and configuration.
- `POST /api/v1/settings/ai-provider/test-connection` — explicitly test the submitted provider, endpoint, model, and optional unsaved key with a short structured prompt that contains no mailbox content. The endpoint may use the saved encrypted key when the request omits one; it never persists submitted settings or returns credentials.
- `GET /api/v1/settings/retention` and `PATCH /api/v1/settings/retention` — read or set the body/attachment cache lifetime in days; default is 60 days and settings are available while East's local key is available.
- `GET /api/v1/mailboxes` — mailboxes visible to the current user.
- `POST /api/v1/mailboxes/connect` — start an explicit mailbox-link OAuth flow for the signed-in app user; return or redirect to a Google authorization URL using `prompt=select_account` and the Phase 2 Gmail scope.
- `DELETE /api/v1/mailboxes/{mailboxId}` — disconnect a mailbox owned by the current user; purge its local cache, credentials, insights, unsaved app drafts, and staged files without changing saved Gmail content. Do not call Google's token-revocation endpoint as part of local disconnect: [Google documents](https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke) that revocation removes every OAuth scope granted to the project, which can also break East sign-in and other linked mailbox access. The confirmation warns that the Google grant may remain until the user revokes East in Google Account settings.
- `POST /api/v1/mailboxes/{mailboxId}/sync` — request or refresh a sync.
- `GET /api/v1/mailboxes/{mailboxId}/labels` — return Gmail system and user labels for that mailbox.
- Mailbox response fields are `id`, `email`, `displayName`, `color`/`colorIndex` (stable while connected; disconnect deletes the local assignment and reconnect can allocate a new color), `syncStatus`, `lastSyncAt`, and the category tabs present for that mailbox. The first eight account colors use Nord accents; additional colors are a deterministic Nord-compatible sequence so connected accounts remain distinct. `syncStatus` is one of `pending`, `syncing`, `ready`, `needs_reauthorization`, `partial_failure`, or `error`; a missing mailbox is represented by the absence of a connection. Never expose OAuth tokens.
- `GET /api/v1/threads` and `GET /api/v1/threads/{threadId}` — list and inspect conversations with mailbox/filter/category/pagination parameters. Show Gmail category tabs using categories available for each account. An explicit search query searches the full Gmail mailbox on demand; load full message details for older matches when the user opens them.
- The same thread routes accept `cacheOnly=true` for ownership-scoped local page/detail reads with no Gmail calls. Conversations requests this before the Gmail refresh so saved lists and still-valid encrypted bodies render immediately. Plain-text local search matches cached subjects and sender fields only and is presented as a partial saved subset; Gmail's full-mailbox search replaces it when available. Gmail operators, quoted phrases, and other query syntax skip local matching and wait for Gmail. Cache-only pagination uses a separate local cursor and remains available if Gmail refresh fails; after refresh succeeds, the UI replaces the saved page and cursor with Gmail's authoritative page and token.
- Thread-list responses include `items`, `nextPageToken`, and `totalEstimate`. Each item includes an East thread ID, mailbox ID and account identity, subject, encrypted-cache-backed snippet (or null), sender, latest message time, unread/starred flags, labels, category, message count, and attachment availability. The API merges account results for the All accounts view and keeps account cursors in an opaque page token.
- Gmail's `threads.list` reference documents pagination, estimates, query and labels, but no result-order contract. The current cross-account merge sorts each buffered page by message time; newest-first ordering is best-effort until validated against Gmail behavior or replaced with a strategy that does not rely on per-account page order.
- Thread-detail responses include account identity, subject, labels, and ordered messages with sender/recipient headers, timestamp, body text and safe-to-render HTML from the encrypted cache or a user-opened Gmail fetch, and attachment metadata. Valid cached bodies are retained when a thread refresh finds additional or expired messages; only missing/expired bodies are fetched. Response IDs are East-owned IDs, not proof of mailbox ownership.
- `GET /api/v1/threads/{threadId}/messages/{messageId}/attachments/{attachmentId}` — fetch an attachment only after a user action, after verifying thread/message/mailbox ownership and granted Gmail scope.
- `GET /api/v1/threads/{threadId}/messages/{messageId}/attachments/{attachmentId}/inline` — serve an owned, unambiguous Content-ID attachment only when its MIME type is GIF, JPEG, PNG, or WebP. Verify the authenticated owner, thread, message, attachment, Content-ID, and source-body/cache lifetime; retain fetched bytes only in the existing encrypted attachment cache with the configured body-cache TTL.
- `PATCH /api/v1/threads/{threadId}` — update supported Gmail-backed state such as read/unread, star, archive, Move to Inbox, trash, Restore from Trash, spam/not-spam, and user labels after verifying user ownership and scopes. Gmail system labels are read-only.
- `POST /api/v1/threads/bulk-actions` — apply an explicit archive, Move to Inbox, trash, restore from Trash, read/unread, spam/not-spam, or label action to user-selected thread IDs; validate ownership and scopes for each thread and return per-item outcomes, including partial failures across mailboxes.
- Bulk-action request shape: `{ threadIds: string[], action: string, labelIds?: string[] }`. The backend processes only the exact selected IDs, validates ownership for each, and returns a result for every requested item.
- `POST /api/v1/mailboxes/{mailboxId}/labels`, `PATCH /api/v1/mailboxes/{mailboxId}/labels/{labelId}`, and `DELETE /api/v1/mailboxes/{mailboxId}/labels/{labelId}` — create, rename, and delete user labels after verifying mailbox ownership and scopes.
- `POST /api/v1/threads/{threadId}/draft-suggestions` — on the user's request, generate an editable app draft without changing Gmail.
- `POST /api/v1/messages/{messageId}/forward-drafts` — create an app-local forward draft from a selected message, including its original attachments by default; the user can remove them before save/send. This does not change Gmail.
- `POST /api/v1/draft-suggestions` — on the user's request, generate an editable app-local draft for a new email without changing Gmail.
- `POST /api/v1/drafts` — create an app-local draft for a new email; the draft may have no source thread.
- `POST /api/v1/drafts/{draftId}/attachments` — attach a user-selected local file of any type to an app draft after checking draft ownership, safe filename, and the 10 MiB per-file, 16 MiB per-draft, and 10-file limits. Do not restrict by extension; use a syntactically safe declared MIME type or `application/octet-stream` fallback. East does not execute or preview outgoing files, and Gmail restrictions still apply when saving or sending.
- `POST /api/v1/drafts/{draftId}/save-to-gmail` — save an app-local new-message, reply, or forward draft to Gmail Drafts after a separate user click.
- `POST /api/v1/drafts/{draftId}/send` — send only after explicit, message-specific user confirmation.
- `GET /api/v1/dashboard` — summaries and insights filtered by mailbox and date range; default to the past seven days when no range is specified.
- Dashboard responses should include whether an AI provider is configured, without exposing credentials, so the UI can show the Configure AI state while keeping Gmail features available.
- `POST /api/v1/dashboard/summaries` — request a one-time summary for a selected date range.
- `PUT /api/v1/reports/daily/settings` — enable or disable a daily report and set its local run time.
- Every Gmail-backed mutation and draft/send endpoint must enforce mailbox ownership, granted scopes, and explicit user action. Bulk operations may affect only the IDs selected by the user and must report per-item outcomes.
- The send review must show To, CC, BCC, subject, body, sending mailbox, and selected attachments before confirmation. For Gmail drafts already saved to Google, East must re-read and fingerprint the current draft, then send the draft ID with a replacement `message.raw` built from that same reviewed snapshot in one `drafts.send` request. This ensures Gmail sends the content the user reviewed even if another client edits the stored draft concurrently.
- Sanitize rich-text HTML on save and render message HTML in a restricted, safe context; preserve a plain-text body for clients that need it.
- Sanitize incoming HTML with the backend's explicit Jsoup allowlist before returning it; remove scripts, styles, event handlers, and active embeds. Rewrite only an unambiguous owned raster cid: image to the authenticated local inline-attachment route. Keep external image URLs in an inert attribute and do not give them a src until the user selects that message's **Load external images** action. Accept only absolute HTTP(S) URLs; reject malformed values, local-only hostnames, and literal loopback/private/reserved addresses. Do not resolve DNS or make a remote request before consent. Set referrerpolicy=no-referrer before assigning remote src; sender-authentication results and inbox classification do not establish remote-image safety. Open permitted email links in a new tab with `noopener noreferrer`, and render To/Cc/Bcc details from the owner-scoped message response.

Do not trust `userId` or `mailboxId` supplied by the browser as proof of access. Resolve the current user from the authenticated server-side session and verify mailbox ownership in every request.

## 8. Assistant processing design

- Start with deterministic computations for thread status, direction, dates, and known Gmail metadata. Use a model only for language tasks such as digest generation or candidate action/transaction extraction.
- Run summary processing only for an explicitly requested report or after the user enables a daily schedule. Generate email drafts only after an explicit user request. A configured API key alone does not enable processing.
- The user confirmed AI-assisted new/reply draft generation for Phase 3. Phase 2 supports manual composition and explicit save/send actions; it does not call a model to generate message text. Model-backed drafts create editable app-local drafts only; saving and sending remain separate user actions.
- If the app missed an enabled daily report while closed, generate one catch-up report for the most recent day on next startup instead of replaying every missed run.
- Send a bounded, relevant message set for the requested window to the summarizer; do not pass an entire mailbox by default.
- Require machine-readable structured output, validate it server-side, and attach each claim to one or more source message/thread IDs.
- Treat email text as untrusted input. Instructions contained in emails must not change the assistant's system behavior or trigger application actions.
- The assistant may recommend or draft but cannot independently mutate Gmail. Every label, read-state, star, archive, trash, draft-save, or send action requires a user-initiated action.
- A request to generate an assistant new-email or reply draft creates an editable app draft only. Saving that draft to Gmail Drafts requires another click; sending requires a separate, message-specific confirmation.
- Only the user may select and add new local files to a draft. A user-created forward includes its source message attachments by default; the user can remove them. Show every filename during review and never attach files based on model output.
- User-selected outgoing attachments may use any file extension, but stay under 10 MiB each, 16 MiB total, and 10 files per draft. Preserve a declared MIME type only when it consists of safe MIME tokens; otherwise use `application/octet-stream`. Send every uploaded file as an attachment, never execute or preview it in East, and leave final acceptance to Gmail's own sending restrictions.
- Encrypt locally stored app drafts and their staged attachment bytes with the local encryption key. Remove staged attachment bytes after a successful save to Gmail Drafts, send, or deletion of the app draft.
- Do not expire unsaved app-local drafts with the message-body cache; retain them encrypted until the user saves them to Gmail Drafts or deletes them.
- The user chooses whether to configure a model provider and supplies its API key. The first release supports OpenAI and a configurable OpenAI-compatible endpoint; native integrations for other providers can be added later.
- Before sending real email content to a configured provider, disclose which provider receives it and link to its current data processing and retention terms. The user can use deterministic features without configuring a model key where possible.
- For a custom endpoint, display the configured base URL and model identifier, and make clear that email content is sent to that endpoint when model features run. Do not claim to know its retention policy.

## 9. Security and privacy requirements

- Keep Google OAuth secrets, refresh tokens, database credentials, encryption keys, and model API keys out of the frontend bundle and source control. A key entered in local settings must be sent only to the local backend, encrypted at rest, never returned to the UI after saving, and excluded from logs. Support replacing and removing it.
- The connection-test action is user initiated and sends only a fixed test prompt, with no email or mailbox-derived data. A newly entered key is used for that one request and is not written to storage; responses and logs exclude provider response bodies and credentials.
- Generate a random 256-bit per-install encryption key and store it outside PostgreSQL in `~/.east/vault.key` by default. Restrict the key and its parent directory to the current OS account on POSIX systems; when loading an existing key, repair the final parent directory's POSIX mode and reject a symlinked parent or key path. Allow an optional `EAST_VAULT_KEY_FILE` override and protect that path with equivalent OS permissions. Keep the loaded key in backend memory while East runs; do not prompt for a routine passphrase or idle-lock the local app.
- Keep East bound to IPv4 loopback. This design encrypts sensitive database records and database-only backups, but the local key file and local database are available to processes running as the same OS account. Spring Session's raw session ID is an opaque bearer lookup identifier stored in the database; HttpOnly and SameSite cookies reduce browser exposure, but do not make that identifier encrypted. Do not claim isolation from other users or malware with access to that account. A lost/unavailable key requires a warned destructive reset; the reset truncates both Spring Session tables so old-key attributes and browser sessions are removed. Gmail data is unaffected and the user signs in again, reconnects accounts, and re-enters provider credentials.
- For an existing installation from the passphrase-based vault version, allow a one-time migration: verify the current passphrase against the encrypted marker, persist the existing derived key to the owner-only key file, then remove the routine passphrase gate. Never store the passphrase. If the user cannot provide it, offer the destructive local reset instead.
- Sync and scheduled reports run while East is open and the local key is available. If East was closed at the scheduled report time, Phase 3 generates one catch-up report for the most recent day on startup. TTL cleanup may run at any time because it only deletes encrypted rows and never decrypts their contents.
- Encrypt refresh tokens at rest; restrict database access to the local service account; redact secrets and email body text from logs by default.
- Use database-backed Spring Session JDBC with Liquibase-managed tables and a 60-day session persistence window. Keep the session cookie HttpOnly and SameSite=Lax, reject and clear malformed cookie identifiers before session lookup, retain session-fixation protection, CSRF protections for session-authenticated state-changing requests, strict CORS/origin configuration, and request validation. Explicit logout invalidates the persisted session.
- Apply user/mailbox ownership checks at service and repository boundaries. On mailbox disconnect, delete the local records, app-only drafts, and derived records tied to that mailbox; do not call Gmail to alter its saved drafts or other messages.
- Encrypt full message body caches at rest, enforce their expiry, and purge mailbox cache and token material when the mailbox is disconnected or the app user deletes their data.
- Make data retention, external model processing, and diagnostics/logging behavior visible in product documentation before release.
- Background sync field masks exclude all MIME `body.data` fields; do not analyze attachment content with AI in the first release. Show available metadata and fetch message body text only when the user explicitly opens a conversation. Opening a message may transiently receive inline file-part data; an inline attachment click may transiently transfer other MIME part data because Gmail's fields syntax projects onto every selected array element. East retains only text for body reads or the clicked part for attachment reads, and removes the other data fields before local caching. Encrypt retained attachment bytes and expire them with the user-configurable message-body cache, except an explicit re-fetch after expiry may start a new TTL; purge them on mailbox disconnect or user-data deletion.
- For attachment previews, allow only explicitly supported safe MIME types (PDF and common raster image types); serve unsupported and active-content types as downloads. Message-body cid: images are limited to GIF, JPEG, PNG, and WebP. External message-body images remain blocked until an explicit per-message click and use no-referrer; no email-supplied script or instruction runs.
- Minimize stored content. Full message bodies use an encrypted cache with a 60-day default lifetime that users can change in settings.
- Changeset 010 promotes a still-live legacy snippet from its existing snippet expiry by the remaining 53 days of the former seven-day default. This is independent of body-cache markers or later body re-fetch timestamps, and expired snippets are never extended.
- Expire generated summaries and extracted insights with the source message bodies, using the same user-configurable cache lifetime.

## 10. Configuration and local setup

Expected local configuration will include values such as:

- PostgreSQL JDBC URL and credentials for the Docker Compose service.
- Google OAuth client ID and client secret in a protected, untracked local config file; the setup guide explains where to obtain them and how to register the localhost callback.
- Exact localhost OAuth callback URL.
- Random local encryption key stored in the owner-only `~/.east/vault.key` file by default. Optional `EAST_VAULT_KEY_FILE` selects a different protected local path; do not put the key itself in an environment file.
- Optional user-supplied model API key entered in East settings; send it only to the local backend and encrypt it in the vault. Never put it in `.env` or the frontend bundle.
- Optional custom OpenAI-compatible endpoint base URL and model identifier; identify this endpoint in the UI before model processing is enabled.

Google OAuth client credentials belong in the protected, untracked root `.env`, not application settings or source control. Create it from `.env.example`, set file permissions to owner-only, and enter the registered redirect URI exactly as configured in Google Cloud. The local encryption key and OpenAI key do not belong in `.env`. Never seed a real user email or commit credentials.

Provide a Docker Compose configuration for PostgreSQL with a persistent local volume and documented start, stop, backup, and reset commands. Keep the API and frontend runnable as local development processes initially; containerizing them can be considered separately.
