# Phase 2 account-scope source review

Date: 2026-11-09

## Scope and method

Read-only review of Google sign-in/mailbox linking, Gmail sync, combined and per-mailbox list/search, mailbox actions and labels, draft composition, disconnect cleanup, and account-color lifecycle. Inspected source and product/technical/roadmap docs only. No `.env`, credentials, tokens, vault key, real mailbox data, browser, Gmail/API calls, edits to application code, builds, or tests were accessed or used. This scratchpad records source evidence, not runtime acceptance.

## Findings

- **Identity model and linking:** `backend/src/main/resources/db/changelog/001-initial-local-schema.sql:11-19,22-44` defines one anchored app user per installation and unique mailbox identity per user. `backend/src/main/java/com/east/app/auth/AuthRepository.java:22-52` anchors sign-in by stable Google subject, not email. `GoogleOAuthService.java:52-64` creates separate sign-in/link intents; `OAuthSessionStateStore.java:31-70` stores random, short-lived, one-use state in the browser session; `GoogleOAuthCallbackController.java:49-61` checks the pending link’s app user against the current session before connecting. This supports additional mailbox identities without hardcoded addresses.
- **Sync scope:** Scheduled sync reads all mailbox targets (`backend/src/main/java/com/east/app/gmail/GmailSyncRepository.java:30-33`), which relies on the one-app-user-per-install schema invariant. Manual sync and on-demand thread loading resolve an owner+mailbox target (`GmailSyncRepository.java:36-43`; `GmailSyncService.java:124-145`). Per-target sync uses that target's mailbox token. This is safe for the documented single-user installation; a future multi-user server would need user scoping on scheduled target enumeration.
- **Combined list/search:** `backend/src/main/java/com/east/app/mailread/MailReadRepository.java:28-49` resolves only the current app user’s mailbox list or an owned requested mailbox. `MailReadService.java:96-112,188-235,238-264,267-344,515-519` maintains independent mailbox cursors, checks a requested label against each mailbox, uses each mailbox’s token, and materializes metadata with both app-user and mailbox scope. `frontend/src/components/Conversations.tsx:1155-1164` sends an optional mailbox ID for single-account mode and omits it for combined mode.
- **Actions and labels:** `MailActionsRepository.java:21-33` resolves an owned thread; `MailActionsService.java:148-225` resolves labels within the thread’s mailbox, uses that mailbox’s access token, and syncs local state with thread+mailbox IDs. Label CRUD also checks app-user/mailbox ownership (`MailActionsService.java:72-145`; `MailActionsRepository.java:43-82,96-128`). Mixed-account bulk label UI partitions selected threads by mailbox and sends account-local label IDs (`frontend/src/components/Conversations.tsx:1483-1514`).
- **Drafts/composition:** `DraftRepository.java:29-59,88-119` scopes mailbox, source-thread, and draft reads by app user and mailbox. `DraftService.java:94-150,154-226` validates ownership and preserves the source mailbox for replies/forwards. Gmail save/send use the draft’s prepared mailbox (`DraftService.java:323-435`); send requires explicit confirmation and review fields (`:378-392`). New-message composition requires an account choice when the request has no selected mailbox, while reply/forward uses its source account (`frontend/src/components/Conversations.tsx:1633-1650`; `frontend/src/components/Composer.tsx:1272-1280`).
- **Disconnect cleanup:** `MailboxService.java:103-112` checks the current user, purges affected summary runs, deletes only the owned mailbox, and invalidates its token cache. Database foreign keys cascade mailbox deletion through threads/messages, attachments, labels, local drafts, and staged draft attachments (`001-initial-local-schema.sql:46-48,73-75,109-112,139-164,186-198`). `product-plan.md:118` and `implementation-roadmap.md:51` explicitly say disconnect purges local data but does not revoke the Google OAuth grant; the UI explains this (`frontend/src/components/ConnectedDashboard.tsx:110-119`). This is aligned with the current decision.

No concrete cross-account ownership or combined-view defect was found in the reviewed paths.

## Account-color follow-ups

- `MailboxService.java:37-46` preserves the existing color index while the mailbox row exists. New assignment is derived from the Google subject hash and adjusted around currently occupied indices (`MailboxRepository.java:107-120`). Disconnect deletes that row, so there is no persistent identity-to-color mapping. In a hash-index collision case, reconnecting after the other mailbox set changes could assign a different color. The product plan now clarifies that stability applies while connected and disconnect purges the local assignment with the mailbox data; no identity-to-color mapping is retained after disconnect.
- The first eight stored indices use Nord swatches; later indices use a deterministic Nord-compatible HSL sequence (`frontend/src/lib/mailbox-colors.ts:1-32`). The product and technical plans now document this behavior so accounts stay distinct without color recycling when the mailbox count exceeds eight.
